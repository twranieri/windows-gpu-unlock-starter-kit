# Experimental Windows unlock for RTX 30 and RTX 40

The desktop preview and the `RTX.ps1` source workflow prepare a local USB unlock
for one or two NVIDIA GPUs using the pinned
`nv-uefi-unlocker` engine. It recognizes 48 RTX 30-branded PCI IDs and 25 RTX 40
PCI IDs from NVIDIA's driver table. It selects Ampere or Ada firmware per card,
including the Ada-based RTX 3050 A Laptop. Cards with different memory sizes use
their own live framebuffer geometry. The Windows memory number is informational.
[NVIDIA device table](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/1a82fbfda8f321b056eb3568850f9316c5e465c5/README.md#compatible-gpus)

The catalog describes which cards can try the experimental workflow. Windows
results depend on the GPU, VBIOS, motherboard, display ownership and power
state. This kit has build and host test coverage. Its own physical boot and
recovery tests are pending. A two-card session can have different outcomes for
the two cards because the engine recovers each card independently.
[Upstream card evidence](https://github.com/physicsdolphin/nv-uefi-unlocker/blob/37327d53dfae1f475638cdb8897b56d3edd4eb20/docs/compatibility.en.md)

> **The desktop preview uses two USB boots.** Run the stock benchmark in
> ordinary Windows first. The first USB boot is the read-only probe. Once Setup
> shows **Probe passed**, the second USB boot runs the unlock. Check Setup's
> status and boot log after each return to Windows. Screen flicker varies by
> hardware. The older capture-based `Start.ps1` workflow has a separate boot
> sequence.

## Hardware qualification

The catalog counts unique PCI device IDs. A single ID can cover multiple boards,
subsystems or laptop models. Full physical qualification of the desktop preview
is still open across the catalog. The examples below distinguish the kit's
validation from upstream reports for specific configurations.

| Catalog group | PCI IDs | Published evidence and limits |
| --- | ---: | --- |
| RTX 30 desktop, including OEM | 23 | Preview 12 checked benchmark readiness on an RTX 3090. The historical physical RTX 3090 result used the capture-based kit. A full Preview 12 trial on the reported HP RTX 3070 Ti is pending. Upstream reported an RTX 3070 `2484` that completed EFI and lost the change in Windows. |
| RTX 30 laptop | 25 | Upstream reported a Windows result on an RTX 3080 Ti Laptop `2420`. The group includes 22 Ampere IDs and three Ada RTX 3050 A Laptop IDs. |
| RTX 40 desktop | 15 | Upstream reported a matched Windows result on an RTX 4060 `2882`. The kit's reported MSI RTX 4090 and ASUS Z890 configuration has fixture coverage with physical testing pending. |
| RTX 40 laptop | 10 | Upstream reported Windows results on an RTX 4060 Laptop `28e0`, with different outcomes depending on the machine's graphics mode. |

[Kit validation by build](../VALIDATION.txt) · [Historical RTX 3090 measurements](ORIGINATING-RESULTS.md) · [Upstream device matrix](https://github.com/physicsdolphin/nv-uefi-unlocker/blob/37327d53dfae1f475638cdb8897b56d3edd4eb20/docs/compatibility.en.md#device-matrix)

For a qualification record, capture the Setup build and EFI binary hashes. For
each GPU, record the PCI vendor, device and subsystem IDs, the bus address in
that run, the VBIOS version and VRAM capacity. Also record the motherboard or
laptop model and BIOS version, Windows build, NVIDIA driver version, and the
graphics setup. Include which cards are installed, which GPU drives the
display, the laptop graphics mode or eGPU connection where applicable, and
whether the run followed a cold boot, resume or driver reset. A result applies
to the configuration and build tested.

1. **Inventory.** Confirm that Windows and NVIDIA report matching PCI device
   and subsystem IDs for every intended card. Record which entries are cataloged.
2. **Read-only probe.** Record which cards were matched and awake in UEFI, and
   whether the probe reached the start of the Windows handoff.
3. **EFI result.** Record the completion status per PCI address and whether the
   log shows a complete handoff. Record incomplete and partial outcomes as such.
4. **Windows result.** Confirm Windows reached the desktop, the EFI log matches
   that startup, and the display and NVIDIA driver work for each intended card.
5. **Matched benchmark.** Save the stock and post-unlock results for each physical
   GPU. Record whether the comparator accepted the pair and the measured result
   with the same driver, runtime and GPU settings.
6. **Windows recovery.** Record whether the machine returned to a normal stock
   boot with working displays and healthy GPU status. Record the repeat stock
   result where available.

## Desktop setup preview v0.4.0

Extract the entire preview ZIP to a local folder. Open
**Windows GPU Unlock Setup.exe** and approve the Windows administrator prompt.
If Setup reports a reparse point, extract a fresh copy to a new local folder
outside OneDrive or other synced folders and reopen Setup from there.
When **Show extraction steps** appears, follow it to start from a fresh folder
with the complete ZIP. The Setup window title shows the build you opened.
The preview uses verified prebuilt probe and unlock EFI applications and an
`assets.exe` generator. The ZIP includes the corresponding engine source.
Git, Rust and a compiler are unnecessary for this path. The app generates
firmware assets locally from pinned, cached inputs. The ZIP contains no
proprietary NVIDIA firmware assets.

Use x64 Windows with the NVIDIA driver and `nvidia-smi`, a keyboard, and one
dedicated, backed-up USB drive. A spare 8–32 GB stick is enough. Setup gives you
one Windows action at a time and verifies each change.

- **Turn off Fast Startup** changes the Windows setting and checks it again.
- **Turn off BitLocker** starts decryption of the Windows drive after your
  confirmation. Save your recovery key first. Setup checks the progress while
  Windows runs and waits for full decryption.
- **Show BIOS steps** guides you through UEFI, Secure Boot and CSM. Only change
  those options after confirming Windows already boots in UEFI mode from a GPT
  disk. Use your PC or motherboard manual for the firmware menu.
- **Format USB** appears for an eligible selected USB that needs FAT32 or whose
  files block setup. If the remaining Windows checks are settings Setup can
  correct, it offers the format first. Check the drive letter, model and size.
  Confirming erases the selected volume. The same confirmation lists any
  Windows Fast Startup or BitLocker changes Setup will make afterward.
- Setup verifies the FAT32 format and the Windows Fast Startup setting. If it
  starts BitLocker decryption, leave Windows running while Setup checks the
  progress. It offers the probe after Windows reaches 0% encrypted with
  protection off and the remaining checks pass.

You can reuse a larger drive that is already FAT32. Copy and verify its
contents on another drive, then clear the old files in File Explorer and
refresh Setup. Keep the existing FAT32 partition.

Keep the ZIP extracted in the same folder through both boots. With automatic
reopening checked, Setup adds a one-time launch at your next Windows sign-in
after a guided step. Approve the administrator prompt when it appears. Setup
looks for the same USB volume and rechecks Windows and the boot log. It clears
the shortcut when the requested comparisons are saved for every detected GPU,
or when you explicitly finish without the remaining comparisons. If an after
test fails, Setup offers a retry and keeps the resume entry enabled when you
selected automatic reopening. Open Setup manually to review results or prepare
another USB later. If you used another account's
administrator credentials, reopen Setup manually.

[Format-Volume](https://learn.microsoft.com/en-us/powershell/module/storage/format-volume) ·
[BitLocker decryption](https://learn.microsoft.com/en-us/powershell/module/bitlocker/disable-bitlocker) ·
[Windows Fast Startup](https://learn.microsoft.com/en-us/troubleshoot/windows-client/setup-upgrade-and-drivers/fast-startup-causes-system-hibernation-shutdown-fail)

1. Plug in one FAT32 USB drive and open Setup. It selects the drive if only one
   qualifies. Check the letter and label, then click **Prepare probe USB**.
   Setup writes and verifies the files. With **Run tensor tests before and
   after unlock** enabled, it also records a stock reading for each GPU that
   needs one. Start this step from Windows Boot Manager and close other GPU
   workloads. Setup looks for CUDA PyTorch. When it needs an environment, it
   downloads about 2.7 GB of pinned Python and CUDA PyTorch files into a private
   folder for your Windows account, verifies CUDA, and runs the stock test.
   Setup also installs the Microsoft Visual C++ x64 runtime if needed. The
   private CUDA 12.6 environment requires NVIDIA driver 561.17 or later and
   10 GiB of free space on the Windows profile drive.
   You can also click **Tensor benchmarks → Set up benchmarks** to install the
   runtime and run the stock test, or **Choose Python** to use an existing one.
   Automatic tests reuse a compatible saved baseline. **Run stock test** records
   a fresh baseline for each detected GPU and keeps the earlier result files.
2. Click **Show first USB boot** and follow the directions for your USB. Fully power
   off and choose the USB in the PC's one-time UEFI boot menu. Let the read-only
   test return to Windows, then reopen Setup and click **Refresh**.
3. When Setup reports **Probe passed**, it has matched the PCI identities,
   confirmed each card is awake in UEFI (D0), and seen the Windows handoff
   start. Choose **Prepare unlock USB**. If Setup cannot get a stock result,
   choose **Retry stock test**, **Continue without comparison**, or **Back to Setup**.
   A GPU needs a stock baseline for a before-and-after comparison. When the USB
   is ready, click **Show second USB boot**, fully power off and select it again. Press **Space** or
   **Enter** at the EFI prompt to confirm. The unlock applies to that boot session.
4. After Windows returns, leave the USB plugged in. Setup checks the EFI log
   against Windows startup history and runs the unlocked tensor test for each
   card with a matching stock reading. A failed after test leaves the comparison
   pending. Use **Retry after test**, click **Refresh**, or reopen Setup in the
   same Windows boot to retry. In a two-card run, Setup still tests the other
   eligible GPU and retains each completed result. Choose **Finish without
   comparison** if you want to end the attempt with results still missing.
   Setup shows completion once every detected GPU has a saved comparison, and
   **View benchmark results** opens the per-GPU results. Use **Open USB log**
   to check the EFI result for each PCI address.
   An EFI result describes the pre-OS transaction. Windows device status and
   workload measurements provide separate evidence. Setup also surfaces Windows
   Device Manager problem codes, such as Code 12 on a card with insufficient PCI
   resources. Check the current session again after sleep or a driver reset.
   [Examples and evidence](COMPARISON.md)

If an unlock boot hangs or fails, fully power off, remove the USB and boot
**Windows Boot Manager** directly. To reset recognized media in Setup, choose
**Restore probe**. Save any log you need first. Restoring clears the USB boot log
and requires a new read-only probe boot before the next staging action.

Setup distinguishes an absent log, an empty or incomplete log, a probe that
rejected a GPU, and an EFI result that failed to hand off to Windows. Follow the
message for the stage you reached. After an EFI result, verify each card in the
current Windows session.

On a detected failure, Setup opens a **GPU-Unlock-Diagnostic-….txt** report.
Review the file and attach it to your support message. If the PC stopped before
Windows could open, boot **Windows Boot Manager**, reconnect the setup USB, and
select it in Setup. Click **Open diagnostics** if a report has not opened. Save
the report before you restore the probe. Setup saves reports locally under
`%LOCALAPPDATA%\WindowsGpuUnlock\Diagnostics` and omits raw EFI logs and
hardware serial numbers.

The VRAM figure shown in Setup comes from the Windows NVIDIA driver. ECC can
reduce the reported total, and the driver may reserve part of the framebuffer.
Setup can prepare the probe when this reading differs from the advertised
capacity or is unavailable. It identifies each card by PCI address, device ID,
and subsystem ID. The EFI unlock checks the live framebuffer layout on each
target. [NVIDIA framebuffer reporting](https://docs.nvidia.com/deploy/nvidia-smi/index.html#fb-memory-usage)

If the loader displays **KIT-STOP** after a transaction error, fully power
off, remove the USB and start **Windows Boot Manager**. The loader saves the
failure and attempts an emergency reset before waiting for power-off. Use
**Restore probe** after saving the log.

### If the tensor benchmark cannot start

Build 14 fixes a stock-validation failure that could occur after the workload
finished and prevent Setup from saving a baseline. Use the complete build 14
ZIP and retry the stock test from a normal Windows boot if an earlier preview
hit that failure.

Extract the full Setup ZIP into a fresh local folder and open Setup from File
Explorer. Use the same account for the Windows desktop and the administrator
prompt. For a stock baseline, boot directly through **Windows Boot Manager** and
close other GPU workloads. In Setup, open **Tensor benchmarks** and click
**Refresh**. Select **Set up benchmarks** if you need the CUDA runtime, or
**Run stock test** if Setup already found it.

A benchmark launch error occurs in Windows before the test starts. Retry from
the desktop with your current firmware settings and USB layout. If the error
persists, go back to Setup and click **Open diagnostics** to see the saved report. The
report records the failed step and any available Win32 error code.

### Offline firmware inputs

On first use the app downloads the pinned NVIDIA source and Arch Linux driver
archive, about 341 MB total. It reuses the verified local cache. If a network
download fails, use **Offline inputs → Download pinned archives** to open them in your
browser. Save both with their original names in one folder, then choose it with
**Offline inputs → Choose archive folder** before **Prepare probe USB**. The generator checks both
archive hashes and the original embedded firmware hashes. The previously pinned
CachyOS archive also works as a verified offline input.
[NVIDIA kernel module source](https://download.nvidia.com/XFree86/NVIDIA-kernel-module-source/NVIDIA-kernel-module-source-610.43.03.tar.xz) ·
[Arch Linux NVIDIA utilities archive](https://archive.archlinux.org/packages/n/nvidia-utils/nvidia-utils-610.43.03-1-x86_64.pkg.tar.zst)

Setup launches the bundled PowerShell scripts with a process-only execution
policy. Windows machine and user policy settings stay in place, and enforced
Group Policy still takes precedence.

From PowerShell, use `-Inputs` with either a local source build or the extracted
preview's prebuilt tools. This example prepares the package in the CLI work
folder, so continue with the CLI probe steps below.

```powershell
.\RTX.ps1 -Action Build -UsePrebuilt -Inputs 'C:\Path\To\FirmwareInputs' -Execute
```

## Command-line source workflow

### 1. Prepare the PC

Use x64 Windows, native UEFI graphics with CSM off, Secure Boot off, a GPT
Windows boot disk, the Windows volume fully decrypted with BitLocker protection
off, and Windows Fast Startup off. Save any recovery key before changing firmware
settings. Use a dedicated, backed-up FAT32 USB data volume and a keyboard.
The kit can reuse a USB it staged for the same package and refuses existing
unrelated files or a different bootloader.

Install Git, the NVIDIA Windows driver with `nvidia-smi`, and Visual Studio
C++ Build Tools with the Windows SDK. Install Rust from Rustup and open an x64
Visual Studio Developer PowerShell in the extracted kit folder.

```powershell
rustup toolchain install 1.95.0-x86_64-pc-windows-msvc --profile minimal --target x86_64-unknown-uefi
$env:RUSTUP_TOOLCHAIN = '1.95.0-x86_64-pc-windows-msvc'
.\RTX.ps1 -Action Check
```

Use the existing [tensor benchmark steps](QUICKSTART.md#4-save-stock-measurements)
to save a stock baseline per card before booting an unlock. Use the same Python,
driver and settings for the unlocked measurements.

### 2. Build locally

```powershell
.\RTX.ps1 -Action Build -Execute
```

Build downloads the pinned public source and checks the included patch. It
compiles distinct read-only and transaction EFIs with the locked Rust dependency
list, and regenerates the required NVIDIA firmware assets locally from hash-pinned
inputs. The first run needs internet access. It writes the build below
`.local/rtx`. For a new GPU set or a rebuild, pick a fresh `-WorkDirectory` and
pass the same directory to the remaining commands.

### 3. Boot the read-only probe

Use an administrator PowerShell for USB actions. Replace `E` with the actual
dedicated USB letter. Commands without `-Execute` preview the action.

```powershell
.\RTX.ps1 -Action Probe -Drive E -Execute
```

Fully power off. Select the USB in the firmware's one-time boot menu and let the
probe hand off to Windows. It records whether UEFI sees the same one or two cards
by PCI address, device and subsystem. Leave the GPU layout and USB target list
unchanged. Keep `loader.log` private. If the probe cannot hand off, power off and
use Windows Boot Manager directly.

### 4. Stage and confirm the unlock

```powershell
.\RTX.ps1 -Action StageUnlock -Drive E -Execute
```

This requires the matching probe log, verifies the package files, then stages
the transaction EFI and the correct assets. Fully power off, boot the USB once,
and press **Space** or **Enter** to allow the transaction. Another key or a timeout
skips it. The EFI rechecks the exact NVIDIA set and requires every selected GPU
to be in D0 before running. The screen can go blank during the handoff.

After Windows returns, check `loader.log` for the outcome on each PCI address and
run the same tensor benchmark per card. A skipped card, failed readback, reset,
or a clean EFI log with unchanged Windows performance needs separate diagnosis.
After a failure, fully power off, remove the USB, and boot **Windows Boot Manager**
directly. The kit uses the one-time boot menu and keeps the read-only loader as a
backup on the USB.
